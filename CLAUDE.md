# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`go-galaxy` is a fast Ansible Galaxy collections installer aimed at CI. It only handles **Galaxy collection sources** - `roles`, git/url/file/dir sources are intentionally unsupported. Drop-in compatibility with a subset of `ansible.cfg` (`[defaults] collections_path`, `[galaxy] server`, `[galaxy] server_list`, `[galaxy] cache_dir`, `[galaxy_server.<id>]`) is a hard requirement. `[defaults] collections_path` may itself be a symlink and install-side writes still work through it, but no component beneath it (`ansible_collections`, a namespace, or a name directory) may be a symlink that leaves the configured tree - not even one whose absolute target geometrically resolves back inside it; see the rooting boundary described under "Install pipeline" below.

## Common commands

The project uses `just` (Justfile) as the task runner.

- `just deps` - `go mod tidy && go mod vendor`. The repo is **vendored** locally, but `vendor/` is git-ignored and never committed - a dependency change commits `go.mod`/`go.sum` only, and CI builds in module mode with no committed vendor tree.
- `just lint` - `golangci-lint run ./... --timeout=5m`.
- `just test` - `go test ./...`.
- `just check` - runs `go vet`, `staticcheck`, `govulncheck`, and `fieldalignment` (all wired through `go tool` directives in `go.mod`).
- `just fix` - `go fix` + `fieldalignment -fix`.
- `just run` - runs `check` + `lint` + `test`, then `go run -race ./cmd/go-galaxy/main.go`.
- `just build` / `just build_linux` - produce binaries under `dist/` with version ldflags injected.
- `just oci [executor=podman] [tag=local]` - builds a Linux binary then a local OCI image.

Run a single test: `go test ./internal/galaxy/store -run TestSnapshot -race -v` (substitute package and `-run` regex). CI (`.github/workflows/ci.yml`) runs `go vet`, `staticcheck`, `govulncheck`, `golangci-lint`, and `go test -race -coverprofile=...`.

## High-level architecture

### Entry flow
`cmd/go-galaxy/main.go` builds a `urfave/cli/v3` app with `install` (default) and `cleanup` subcommands. Both commands follow the same pattern (see [install.go](cmd/go-galaxy/commands/install.go) and [cleanup.go](cmd/go-galaxy/commands/cleanup.go)):

1. `config.BuildCollectionConfig(c)` - merges CLI flags, env vars, and `ansible.cfg` into `*config.Config`. Anything taken from `ansible.cfg` is flagged via `Ansible*Used` booleans for debug logging.
2. `progress.New(verbose, quiet)` - a `Printer` that captures `log` output and renders spinner/progress UI.
3. `infra.New(printer, http.Client)` - the runtime container (`Output`, `HTTP`, `Now`, `TempDir`) threaded through every subsystem. Prefer extending `Infra` rather than passing more globals.
4. Dispatches to `collections.Start` or `cleanup.Start`.

### Cache backend abstraction
The `cacheManager.Backend` interface in [internal/galaxy/cache/backend.go](internal/galaxy/cache/backend.go) is the single seam between business logic and persistence. Two implementations:

- [internal/cache/local](internal/cache/local) - filesystem under `cfg.CacheDir`; uses Bolt files for state and a directory layout for tarballs.
- [internal/cache/s3](internal/cache/s3) - S3-compatible object store (selected when `--s3-bucket` / `GO_GALAXY_S3_BUCKET` is set). Includes its own minimal S3 client, distributed locking via conditional `PUT` + lock TTL, and gzip-on-the-wire for the snapshot.
- The S3 backend's `LoadStore` checks the persisted schema version via a lightweight meta-only probe before decoding the full payload, matching the local backend's schema-first `Load` order.
- `Backend` also exposes `SweepTemp(ctx)`, called once by `initInstall` while the exclusive lock is held. The local backend removes leftover `.download-*` files from the cache directory; the S3 backend is a no-op, since its download temps live under the OS temp directory instead of the shared cache.
- **Trust model:** the S3 snapshot object and the project registry object are a trust boundary. `Backend.LoadStore`/`LoadProjectRegistry` serve cached Galaxy metadata (including an artifact's download URL and sha256) without re-validating it against the origin on every use, so a principal who can write the bucket can influence what a run installs. The same registry write also reaches `cleanup`: an injected project record drives deletions rooted at an attacker-chosen `<CollectionsPath>/ansible_collections/<ns>/<name>`, plus an arbitrary-path YAML read through that record's `RequirementsFile`. Operators must restrict bucket write access (a write-restricted ACL or dedicated credentials), just as they would protect the local cache directory; the local Bolt snapshot is implicitly trusted for the same reason, since writing it already requires local filesystem access to the cache directory. Both state-object reads are size-capped (`helpers.StateObjectMaxCompressedSize`, `helpers.StateObjectMaxDecompressedSize`), so a hostile-but-writable bucket cannot OOM the process with an oversized object or a gzip bomb. The cache-hit artifact fetch (`fetchArtifact`'s cache-hit arm reading through the S3 backend) is in scope for `helpers.ArtifactDownloadDeadline` (see "Install pipeline" below), since it streams a full artifact body over HTTP just as a fresh origin download does. The whole-run hold on this same lock is unbounded by design - a hostile or slow server can inflate it through either the metadata resolve or the artifact phase - and that is accepted rather than capped because taking the lock already requires bucket write access, the same boundary this bullet establishes; see `loadVersionsListCached`'s doc comment (`internal/galaxy/collections/resolve.go`) for the full reasoning.
- **Artifact digest shape enforcement:** an artifact sha256 arriving from either trust boundary above - the persisted snapshot's `InstalledEntry`/`WarmedEntry` sha, or a Galaxy server's `artifact.sha256` - is checked against `helpers.IsSHA256Hex` before it is used to build an extract-marker path or persisted any further. The content-addressable extracted store keeps its own, separate guard on the same identifier - `extracted.entryRel` rejects anything that is not a single safe path element via `helpers.IsPathElement` - so a warmed-record sha reaching `extracted.Store.Ready` is bounded by that check rather than by the digest-shape one. The read side degrades gracefully: `checkExtractMarker`/`verifyExtractMarker` treat an unsafe sha as "not verified, re-extract", never as a value to act on. The producer (`resolveArtifactSHA`), the marker writer (`writeExtractMarker`), the extraction entry point (`extractCollection`), and the lockfile writer (`buildLockfile`) instead fail closed with `helpers.ErrMalformedArtifactSHA256`. That sentinel sits outside `ErrSHA256Mismatch`'s retry class in `prepareWithRecovery`'s `prepareInstall`-error arm specifically, because eviction-and-refetch cannot repair a value that was never a valid digest to begin with - and it does not except itself from that same function's separate, deliberately unclassified action-error arm, which still evicts on any action failure regardless of cause. `cmd/go-galaxy/exitcode` classifies both `helpers.ErrMalformedArtifactSHA256` and `helpers.ErrSHA256Mismatch` as `ExitIntegrity` (7), a class checked ahead of the lock/install/network ones precisely so a malformed digest is never mistaken for one of those; `lock` inherits this without any change to `buildLockfile` itself - the same sentinel that used to fall through to the generic exit code (1) as an unrecognized error now maps to `ExitIntegrity` purely because `exitcode` gained a case for it. A resolved collection's version has the identical shape-enforcement story, on the identical two trust boundaries: a value arriving from a persisted snapshot's `ResolvedEntry.Version`, or from a lockfile entry loaded off disk, is checked against `helpers.IsExactVersion` before it is used to build an install path or committed any further - never trusted merely for being non-empty. Three producers enforce this, all failing closed rather than silently treating an unresolved constraint as installable, and the two that matter most guard genuinely different surfaces rather than duplicating each other: `lockfile.File.validate` (reached through every `lockfile.Load`) is the READ boundary, and it is the only one of the three that `hash`, `tree`, `explain`, and `outdated` ever reach - none of those four commands calls `buildCollectionsMap` or touches `internal/galaxy/collections` at all, so a lockfile carrying an unresolved constraint would otherwise reach them unfiltered. `buildCollectionsMap` is the ACT boundary: the backstop for every resolution path that reaches real install/warm work, lockfile-driven or not, including a poisoned snapshot's `ResolvedEntry` arriving with no lockfile involved in the run at all - a case `lockfile.File.validate` structurally cannot see, since nothing was loaded from disk. `buildLockfile` is the third producer, guarding the write side so `lock` can never commit an unresolved constraint to a new lockfile in the first place. `constraintSatisfied` and `buildResolvedSnapshot` are deliberately left lenient - the former exists to evaluate a constraint, which is exactly the "*"-shaped input this guard rejects elsewhere, and the latter's job is to reconstruct a previously-recorded resolution rather than to police one - so tightening either would turn a poisoned snapshot from a loud, classified failure (`helpers.ErrInvalidCollectionVersion`, `ExitUsage`) into a silent, unexplained re-resolve instead.
- **A cache must not be shared between principals holding different Galaxy credentials.** Cached API responses, resolved versions, dependency graphs, and artifacts are keyed by server (`helpers.ScopedDepsCacheKey`, `helpers.ArtifactKey`), not by which token fetched them, so an entry a privileged run fetched from a private server is served as-is to a later run against the same server with no token at all. Keying by a token fingerprint instead was considered and rejected: it would put a credential-linked identifier into the shared, less-trusted cache, which is exactly the boundary this design keeps clean. This is on top of, not instead of, the trust-boundary restriction above.
- No token, and no value derived from one - not even a hash - is ever persisted: not to the Bolt snapshot, the S3 snapshot, the project registry, the lockfile, the metrics file, or GALAXY.yml. See `config.Secret` below.
- `warnIfOffServerDownloadHost` (in `internal/galaxy/collections`) warns, rather than blocks, when an artifact's download host differs from the configured Galaxy server host: the download URL can originate from a poisoned snapshot, but a legitimate deployment may still serve downloads from a separate content host or object storage.
- **State-object deadline:** `helpers.StateObjectDeadline` (1 minute) bounds one persisted cache-state operation on the `Backend` seam - `LoadStore`, `SaveStore`, `LoadProjectRegistry`, `RecordProject` - end to end, including a lazy `Open` an S3 backend performs inside them, the object GET/PUT, the inflate, and every S3-verb retry, as one shared budget. Its radius is larger than a single request for a reason specific to this seam: `LoadStore`/`LoadProjectRegistry` both run after `initInstall`/`initCleanup` take the exclusive distributed lock, whose heartbeat keeps renewing its TTL in the background, so a stalled read here does not just hang one run - it locks out every runner sharing the bucket until each one's own lock-wait ceiling expires. `internal/galaxy/cache::WithStateDeadline` is a `Backend` decorator, not nine separate `context.WithTimeout` call sites: `initInstall`/`initCleanup` wrap the backend with it once, immediately after construction and before `Open`, and every downstream `SaveStore`/`LoadStore`/etc. call site (`finalizeInstall`, `warmWithState`, `lockWithState`, `saveDryRunSnapshotIfPersisted`, `finalizeCleanup`) is unmodified. It bounds `LoadStore`, `SaveStore`, `LoadProjectRegistry`, and `RecordProject` only; `Open`, `Close`, `Lock`, `ClearFiles`, `SweepTemp`, and `Artifacts()` pass through unbounded - `Lock` because the lock protocol carries its own timings (bounding it with this budget would break contention outright), `ClearFiles` because a bulk delete's legitimate cost is proportional to bucket size and has no fixed ceiling, and the rest because they carry no drippable response body. Like the artifact and metadata deadlines, the budget lives at this seam - never inside `internal/cache/s3` or `internal/cache/local` - which is structural for the local backend specifically: `local.Backend`'s state methods all ignore their context parameter, so the decorator is inert for them by construction. `helpers.ErrStateObjectDeadline` renders its cause with `%v`, never `%w`, is never retried, and is not configurable (`Infra.StateObjectDeadline` is test-only); `cmd/go-galaxy/exitcode` classifies it by WHEN it aggregates, not where it was hit: whenever a tail `SaveStore` failure is folded into another sentinel via `annotateSaveFailure`, the joined error classifies as that other sentinel's own exit class, whatever it is - `ExitInstall` behind `helpers.ErrInstallationFailed` (`finalizeInstall`/`warmWithState`, gated on at least one recorded per-collection failure, identical to the metadata and artifact deadlines' own aggregation shape), `ExitLock` behind `helpers.ErrLockfileDrift` (`lockFrozen`'s own drift verdict, gated on the fresh resolve actually disagreeing with the lockfile on disk) - and whenever it is not aggregated behind anything, it classifies `ExitNetwork` on its own. Unaggregated is the common case: most runs record neither a per-collection failure nor lockfile drift, so a clean run's own tail `SaveStore` failure - along with every init-time operation and every path through `saveDryRunSnapshotIfPersisted`, none of which ever aggregates - lands here. Never `ExitInterrupt` either way.
- **Cache-backend failure classification:** a backend speaks `helpers.ErrCacheBackendUnavailable` when it could not reach its store, or reached it and got back a failure that is not this program's own doing; `helpers.ErrCacheBackendUnusable` when the configured store cannot serve as one - it is missing a guarantee this tool requires, cannot even be turned into an address, or answers a request with an HTTP redirect rather than serving it (the S3 client refuses every redirect, since SigV4 signs the `Host` header and the canonical URI so no followed hop can carry a verifiable signature, and it does so on its own private `http.Client` copy, leaving untouched the redirect-following the shared `internal/galaxy/fetch` client depends on) - so no retry can help and the only remedy is a configuration change; and `helpers.ErrCacheBusy` when another holder already has it. No sentinel carries more than one of these three classes; `internal/cache/s3/variables.go`'s partition doc is the source of truth for which S3-package sentinel carries which. The local backend's own empty-`--cache-dir` sentinel (`helpers.ErrCacheDirEmpty`) is neither: it is a config-usage error under `ExitUsage`, so the same operator mistake classifies identically regardless of which backend hit it. The wrap into one of the three classes lives at the producer of the failure, never at the `Backend` seam, because only the producer knows which of the three applies; a shared budget, by contrast, stays at the seam, for the same reason `WithStateDeadline` above does. `internal/cache/s3/client.go`'s `Client.do` is the single transport funnel behind `helpers.ErrCacheBackendUnavailable`: every `c.client.Do` call in the package goes through it, and it normalizes a transport failure into that sentinel only when the caller's own context is still live (`req.Context().Err() == nil`) - a failure racing a caller's own cancellation is returned unlabeled instead, since the caller's decision to stop outranks blaming the backend. It discriminates on the caller's context rather than on the error's shape, because a `net.Dialer` timeout and `http.Transport`'s `ResponseHeaderTimeout` both satisfy `errors.Is(err, context.DeadlineExceeded)` while the caller's context is still live, so an error-shape test would silently exclude the two commonest outage shapes - a black-holed endpoint and one that accepts a connection and never answers. That labeling decision has a second consumer: `Client.do` mints `errS3TransportFailed` (its own sentinel, produced nowhere else) and `internal/cache/s3`'s retry classifier retries exactly that sentinel, so those same shapes are the only ones this package retries without the remote ever having answered - which on a surface carrying no wall-clock budget of its own (`Open`'s bucket HEAD, an artifact `Has` probe, `ClearFiles`) multiplies the worst-case wait by `s3RetryMaxAttempts` plus its backoff. `cmd/go-galaxy/exitcode` adds `ExitCacheBusy = 8` for `helpers.ErrCacheBusy` and `helpers.ErrAnotherInstanceIsRunning`. `ExitCacheBusy` on the S3 backend requires a positive observation of another acquirer during the wait; a wait ceiling that elapses without one is `helpers.ErrCacheBackendUnavailable` (`ExitNetwork`), so exit `8` never covers a backend that answered nothing - `internal/cache/s3/variables.go`'s partition doc is the source of truth for the two lock-wait sentinels. A fourth class sits outside this three-way partition: `ExitCacheCorrupt` (`helpers.ErrCorruptProjectRegistry`, `helpers.ErrStateObjectTooLarge`, `helpers.ErrCorruptSnapshotStore`) applies whenever the persisted cache state itself - not this reader's ability to interpret it, and not the backend's ability to reach it - cannot be used by anyone and must be discarded before the run can proceed; no sentinel carries this class alongside any of the three above, the identical single-class invariant this bullet already states for them. `helpers.ErrUnsupportedSchemaVersion` is deliberately excluded from it and stays `ExitUsage` instead: a schema version newer than this binary understands means the object was written correctly by a newer binary, not that its bytes are damaged, so the remedy is an environment change (a newer binary, or pointing at a different cache), never discarding data a newer binary's other runners still depend on. `helpers.ErrCorruptSnapshotStore` is local-backend-only, by construction rather than by any check that filters it: `internal/galaxy/store`'s `openBolt` is its sole producer, reached only through the local backend's Bolt file open, and it fires when that open fails one of a closed set of bbolt's own corruption checks (`ErrInvalid`, `ErrVersionMismatch`, `ErrChecksum`) - deliberately not a catch-all, since `bolterrors.ErrInvalidMapping` (an mmap failure) and every OS-level open failure (permission denied, a directory in the file's place) are environment problems rather than damaged bytes and stay unclassified. The S3 backend's state object is gzipped JSON with its own sentinels (`helpers.ErrCorruptProjectRegistry`, `helpers.ErrStateObjectTooLarge`) and never reaches `helpers.ErrCorruptSnapshotStore` at all - the two backends land on the same exit class for the analogous failure through different sentinels, not through one shared code path.

- **`outdated` is the one collection command that opens no cache backend.** It therefore never takes the exclusive lock, serves no cached metadata, and leaves every cache-shaped flag with nothing to act on; those flags are announced once on stderr rather than rejected, because the same values also arrive from an ambient CI environment block where a parse error would be the harshest possible outcome for the least harmful mistake.

`internal/cache/cache.go::New` is the factory that picks one based on `cfg.S3Cache.Enabled`. **Add new backends here**, and make sure they implement `Backend` and return an `ArtifactStore`.

### Snapshot store
[internal/galaxy/store](internal/galaxy/store) defines `Store` - the in-memory representation of cached state (API responses, deps cache, installed collections, dependency graph, resolved versions, project registry). It is bucket-mapped to BoltDB files locally and serialized as gzipped JSON for S3.

- `helpers.StoreSnapshotSchemaVersion` gates compatibility; bumping it requires a migration path. `store.ValidateSchema` rejects newer schemas.
- The current snapshot schema version is 6, bumped when the snapshot gained a warmed set (`helpers.StoreBucketWarmed`, `Store.Warmed`): the collection keys `warm` materialized into the content-addressable extracted store, which `cleanup` must keep even though `warm` never writes an installed entry - see "Cleanup pipeline" below. At persist time, entries in the `APICache`, `DepsCache`, and `Versions` buckets are age-evicted against `helpers.CacheEntryMaxAge` (30 days) and stamped at write time; `Warmed` is age-evicted the same way but against its own `helpers.WarmedEntryMaxAge` (also 30 days, kept as a separate constant since it governs how long real on-disk content stays protected rather than how long cached metadata stays fresh). Eviction judges each entry against a closed window `[now - maxAge, now]` built from a single wall-clock sample per pass (`retentionWindow`), so a write stamp in the future is treated as expired rather than immortal. All of this happens inside the shared `snapshotData()` copy path, so both the local Bolt `Save` and the S3 `MarshalSnapshot` inherit the same eviction for every bucket, `Warmed` included. The migration path for a schema bump is drop-and-rebuild: a snapshot persisted under an older schema is dropped rather than migrated in place, and its caches rebuild cold on the next run - for schema 6, a schema-5 snapshot simply has no warmed bucket, so drop-and-rebuild already lands on the same empty set any field-level migration would have produced. The bump is deliberate despite being purely additive: without it, an older binary sharing an S3 cache would silently drop the `warmed` key on its next save and re-expose the bug this schema fixes, so a loud failure on the old binary (rather than silent data loss) is the intended outcome.
- **Two meta timestamps, two questions.** `Meta.LastSnapshot` is stamped by every persisted write and answers only "does a snapshot exist"; `Store.WasPersisted` reads it. `Meta.ContentRecorded` is stamped only by a write whose store actually held an installed or warmed entry, and `Store.HasRecordedContent` reads it - that is the predicate a pass which deletes on-disk content must consult. The two differ on one reachable shape: `lock` is a real command that writes neither installed nor warmed entries, so on a cache with no prior snapshot it produces one whose content sets are both empty and whose `LastSnapshot` is stamped. Read through `WasPersisted`, that emptiness says "nothing is installed or warmed anywhere" - which is how a plain `lock` on a machine whose snapshot a schema bump dropped, but whose extracted trees survived, hands the next `cleanup` the evidence to wipe the whole content-addressable store. The stamp is derived inside `stampSaveMeta` - the single place where both the local Bolt `Save` and the S3 `MarshalSnapshot` decide what a snapshot claims about itself - rather than passed in per command, so no command can set it wrongly; and it is read from the live store BEFORE `snapshotData`'s age eviction, so a cache whose last content record ages out on this very save does not lose the evidence that it ever existed. Once set it carries forward, which is what keeps the predicate true for a cache whose last collection was legitimately cleaned up: the snapshot genuinely knows nothing is installed there, and that is evidence rather than ignorance. No schema bump is needed - an absent key reads as the conservative answer, so an older binary sharing the cache can only make a destructive pass do less, never more.
- **`Installed` deliberately has no retention window, unlike `Warmed`.** A project whose workspace is gone is skipped by every `cleanup` run, so its keys never reach that pass's would-remove set and the shas its installed entries name are kept in the extracted store indefinitely; the consequence is disk growth in a reconstructible layer, and `--clear-cache` is the existing remedy. A window here would cost more than it recovers, because an already-installed collection is skipped before `recordInstall` is ever reached: a stable cache in its steady state stops refreshing its entries entirely, so they would age out from under a live project and take its extracted trees with them. What would change this is a rule keyed on evidence rather than the clock - a project whose registry entry names both a requirements file that is gone and a workspace that is gone is dead by two independent signals - which is a cleanup-pass design, not a snapshot-schema one. The reasoning is recorded in place at the copy site in `snapshot.go`.
- All `Store` methods are protected by an internal `RWMutex`; do not access fields directly across goroutines.
- `RecordProject` keeps a per-project registry consumed by `cleanup` to compute reachability across all known requirements files.

### Galaxy server resolution and authentication
`internal/galaxy/config/servers.go::resolveServers` computes `cfg.Servers` (`[]config.Server`, never empty on success) from `--server`/`--token`, `[galaxy] server_list` (or `ANSIBLE_GALAXY_SERVER_LIST`), and `[galaxy_server.<id>]` sections, per the precedence documented on `resolveServers` itself. `[galaxy_server.<id>]` accepts `url`, `token`, `validate_certs`, and a no-op `api_version=v3`; `username`/`password`/`auth_url`/`client_id` (ansible's Basic auth and Keycloak/SSO token exchange, neither implemented here) are a hard config-load error naming the key, and any other key only warns.

A token is never a bare string: it is wrapped in `config.Secret`, which renders a fixed redacted placeholder for every serialization path (`fmt`, JSON, YAML) and exposes its plaintext through exactly one deliberately loud, greppable method, `Reveal`. The only call site in the whole program is `cmd/go-galaxy/commands/install.go`'s `serverAuths` - invoked by every collection command via `runCollectionCommand` → `newHTTPClient`, not just `install` - which builds `internal/galaxy/fetch`'s `[]ServerAuth` immediately before constructing the HTTP client. Do not add a second call site, and never let a revealed token reach a log line or persisted state.

`internal/galaxy/fetch`'s `authTransport` (token attachment) and `tlsDispatchTransport` (per-origin `InsecureSkipVerify`) both dispatch by the request URL's normalized **origin** (`helpers.Origin`), never by server id, configured URL, or a prefix/substring match - so a download URL sourced from a poisoned snapshot can never exfiltrate a token or downgrade TLS for a host that merely resembles a configured server.

`internal/galaxy/collections/server_candidates.go` walks `cfg.Servers` in list order for an unpinned collection (first match wins; unlike ansible, results are never unioned across servers) or resolves a `requirements.yml` `source:` to exactly one server. `metadata.go`'s root-metadata fetch is fail-closed: only a 404 across every API-root candidate of one server advances the walk to the next server; a 401/403 (`helpers.ErrGalaxyAuthFailed`) or an exhausted retry budget on a 5xx/network failure (`helpers.ErrGalaxyServerUnavailable`) aborts the whole run naming that server instead. Both exit with the network exit code; every Galaxy-server *configuration* error (a bad section, a rejected key, a policy violation) exits with the usage code instead - see `cmd/go-galaxy/exitcode/exitcode.go`'s `isGalaxyServerConfigError`.

`helpers.MetadataFetchDeadline` (2 minutes) is the metadata-fetch analogue of `helpers.ArtifactDownloadDeadline`: a whole-request wall-clock ceiling on one Galaxy metadata GET - the response, the size-limited body read, and every retry attempt and backoff sleep in `fetchJSONBody`'s `helpers.Retry` loop - as one shared budget, established once around that loop in `internal/galaxy/cache::fetchJSONBody`, the single owner of a metadata request's unit of work (never inside `internal/cache/*`, so nothing crosses the `Backend` seam, and never in `collections/compat.go`'s thin `fetchJSONWithCachePolicy` wrapper, which owns nothing). It exists for the identical reason the artifact deadline does - a byte-drip response defeats the read-inactivity watchdog by always making genuine progress - and it matters earlier: metadata is the first network contact in every command, including every `--dry-run`, ahead of any artifact acquisition. `internal/galaxy/cache::deadlineError` is this surface's normalizer (shared with the state-object deadline below); unlike `artifactDeadlineError`'s ambient rule, it adds a causal precondition - the error being normalized must itself carry `context.DeadlineExceeded`/`context.Canceled` - because a `*cacheManager.HTTPStatusError` racing the deadline must keep routing the server-list walk by status (404 advances, 401/403/5xx abort) rather than being relabeled into the deadline sentinel. The versions-list paging loop (`loadVersionsListCached`) is the one place a per-request budget is not enough: since the server itself controls how many pages a resolve issues (`meta.count`), the loop establishes one shared budget for the whole `maxVersionPages`-bounded loop instead of one per page. Like the artifact deadline, `helpers.ErrMetadataFetchDeadline` renders its cause with `%v`, never `%w`, is never retried, and is not configurable (`Infra.MetadataFetchDeadline` is test-only). `cmd/go-galaxy/exitcode` classifies it exactly like the artifact deadline: `ExitNetwork` unaggregated, folded into `ExitInstall` once joined behind `helpers.ErrInstallationFailed` by a metadata re-resolution inside an install worker, never `ExitInterrupt`.

Because two servers can publish the same `namespace.name@version` with different dependency graphs or artifacts, the deps cache and the artifact store key per server (`helpers.ScopedDepsCacheKey`, `helpers.ArtifactKey` - see the trust-model note above on why this is not the same thing as keying per credential). `installEntryMatches` also compares a candidate's recorded `InstalledEntry.Source` against the collection's currently-resolved source, so a collection whose server changed between runs (a `source:` edit, a server reordering, or a different server winning first-match) is reinstalled rather than silently kept just because its path and version still line up.

### Install pipeline (`internal/galaxy/collections`)
`collections.Start` → `runInstall` orchestrates. `runInstall` owns the backend lifecycle (open, lock, and their release/close defers) while `installWithState` owns the actual work against the already-initialized state - the same lifecycle/work split `runWarm`/`warmWithState` and `runLock`/`lockWithState` use:

1. `initInstall` - open backend, acquire backend lock, load `Store`, optionally clear caches, record this project.
   After acquiring the lock and before loading the store, `initInstall` sweeps dead-run temp orphans: leftover `.download-*` artifact temps and the extracted store's `ingest-*` / `<sha>.tmp` directories. This is safe only because the exclusive lock guarantees no other run is mid-write, and it is best-effort - a sweep failure just logs a warning and the install proceeds.
2. `prepareInstallPlan` - load + parse `requirements.yml`, resolve transitive deps (`resolve.go`), build `collections` map keyed by `<ns>.<name>@<version>`, kick off the prefetcher, then topologically split into `levels` (`buildInstallLevels`).
   Under `--dry-run`, `installWithState` substitutes `installDryRun` for `installLevels` and `finalizeInstall` (steps 3 and 4 below) - it does not run its own pipeline, just this one substituted step after `prepareInstallPlan`: it reports what install would do (`classifyDryRun`), then saves the resolve-side caches through `saveDryRunSnapshotIfPersisted`, which saves the whole store only when `Store.WasPersisted()` was already true before this run - mirroring `finalizeCleanup`'s identical guard in `internal/galaxy/cleanup`. The reason for the guard: every `Save`/`MarshalSnapshot` stamps `Meta.LastSnapshot` unconditionally, so saving from a run against a cache with no persisted snapshot would create one where none existed - a write a later command reads as an assertion about reality, which is exactly what `--dry-run` must not make. What such a snapshot would assert about installed and warmed content is separately defused by `Meta.ContentRecorded` (see "Snapshot store" above), but this guard stands on its own and is not conditional on that.
   `warmWithState` draws the identical substitution: under `--dry-run` it calls `warmDryRun` in place of `warmCollections`, and reuses `saveDryRunSnapshotIfPersisted` unchanged. The guard matters even more here: a warm-only machine has no `ansible_collections` workspace at all, so its extracted trees are protected solely by the warmed set, and a fabricated persisted-and-empty snapshot would hand a later `cleanup` run the evidence to wipe the whole content-addressable store with nothing on disk to rebuild it from. `dryRunBanner` fires from `initInstall`, so every collection command that can be in dry-run mode passes through the same emission point - making "no command is in dry-run mode silently" a structural property of `initInstall` rather than a convention each command must remember to uphold.
   The governing rule for what `--dry-run` suppresses: the command's product (the install itself, or the lockfile `lock` writes); destructive side effects (`--clear-cache`); any write another command later reads as an assertion about reality (the install record, project registration - see `recordProjectUnlessDryRun`'s own doc comment for why an enrolled-but-never-installed project would corrupt a later `cleanup` run - and `saveDryRunSnapshotIfPersisted`'s refusal to manufacture a persisted snapshot where none existed, for the identical reason); and externally consumed reports (the metrics file, since a dashboard cannot distinguish a dry run's numbers from a real run's). Everything else proceeds unchanged - `sweepDeadRunTemps` is the deliberate example: it always runs, dry run or not, because what it deletes is provably a dead-run orphan, never a write another command treats as real. `--frozen` and `--dry-run` are orthogonal, not overlapping: `--frozen` governs the verdict a command's write would have had, `--dry-run` governs whether that write happens at all - on every command but `lock` only the latter is ever in play, while on `lock` the two compose, `--frozen` checked first (see `lockWithState` below) since both suppress the write and the stricter verdict must win.
   `install`, `warm`, `lock`, and `cleanup` implement `--dry-run`; `outdated` implements no dry-run branch of its own, and the flag reaches it through exactly one shared guard - `writeRunMetrics`'s own `cfg.DryRun` suppression of the metrics report (see "Cache backend abstraction" above for the rest of `outdated`'s own shape). Once the fresh resolve has run and the lockfile is built in memory, `lockWithState` checks `cfg.Frozen` before `cfg.DryRun` - both suppress the write, so the order decides which verdict wins, and the stricter one (`cfg.Frozen`) is checked first. When `cfg.Frozen` is set, `lockWithState` calls `lockFrozen` in place of `lockfile.Save` and the "Lockfile written" announcement, and never reaches its own `cfg.DryRun` branch at all - `lockFrozen` honors `--dry-run` itself, through `saveLockSnapshot` below, so a caller does not need two branches to get the composed behavior. `lockFrozen` is `lock`'s drift gate: it compares the fresh resolve against the lockfile already on disk (`lockfile.Compare`) and fails the run with `helpers.ErrLockfileDrift` on any difference rather than overwriting the file - "the lockfile is law" applied to the one command that would otherwise rewrite it, the same way install/warm `--frozen` already refuse to install anything the lockfile does not name. It deliberately mirrors `lock`'s own resolution rather than checking against upstream publication, and it does so per flag set, not per command: what the gate compares against is whatever `lock --<those flags>` would write. Under `--frozen` alone the fresh resolve reuses the persisted resolve snapshot whenever `requirements.yml` and the effective server list are unchanged, exactly as an ordinary `lock` run would, so publishing a newer version without touching `requirements.yml` reports "up to date" - the gate's contract is "running `lock` right now would not change this file", never "every locked collection is still the newest available". Add `--refresh` and the mirrored command changes, not the gate's own logic: `lock --frozen --refresh`'s fresh resolve vetoes that same snapshot reuse (see `--refresh`'s own paragraph above), reaching the live servers instead, so it now gates upstream publication too - `lock --frozen` alone answers "does this file match the requirements", `lock --frozen --refresh` answers "does this file match what `lock --refresh` would write right now", a strictly larger question. `outdated` remains the tool for a third, different question this gate never answers even with `--refresh`: which locked collections have a newer version available, independent of whether resolving would actually pick it up. A missing lockfile is reported as `helpers.ErrLockfileMissing`, not drift, since `lockfile.Compare(nil, fresh)` would read every collection as Added; a lockfile that exists but fails to load fails closed with `helpers.ErrLockfileInvalid` through a direct `lockfile.Load` call, deliberately not through `lockDryRunBaseline`'s lenient policy below - `lockFrozen`'s whole verdict depends on what is already on disk, so it cannot afford to treat an unreadable file as "no baseline yet" the way a command that only ever overwrites the file safely can. `lockfile.Load`'s own contract is what makes this split exhaustive rather than best-effort: every error it returns is either `IsNotExist` or `helpers.ErrLockfileInvalid`, never a third, unclassified shape, so a directory or a permission-denied file sitting at the lockfile path lands on the identical `ErrLockfileInvalid` arm a bad schema version or unparseable YAML already did, not on some error class none of `lockFrozen`, `resolveOrLoadLockfile`, or `lockDryRunBaseline` was written to handle. The other arm of that same dichotomy - the file is simply absent - is turned into `helpers.ErrLockfileMissing` by `lockfile.LoadRequired`, the loader every command that cannot proceed without a lockfile goes through (`install --frozen`, `warm --frozen`, `lock --frozen`, `tree`, `explain`, `outdated`), so that classification is a property of the loader rather than of each call site; `hash` deliberately stays on `Load` and branches on `IsNotExist` itself, since there a missing lockfile is not a failure but the trigger for its requirements-file fallback. Only once neither the missing nor the unloadable case applies does `lockWithState` check `cfg.DryRun` and call `lockDryRun` in place of `lockfile.Save` and the "Lockfile written" announcement. `lockDryRun` loads whatever lockfile already sits at the target path (`lockDryRunBaseline`), diffs it against the freshly built one (`lockfile.Compare`), and reports the difference (`reportLockfileDiff`) instead of writing anything. `lockDryRun` and `lockFrozen` both save the snapshot through one shared rule, `saveLockSnapshot`: `saveDryRunSnapshotIfPersisted` under `cfg.DryRun`, a plain `SaveStore` otherwise - one rule with two callers specifically so a `--frozen --dry-run` run's save behavior cannot drift from a plain `--dry-run` run's, since lock's resolve-side metadata caches are the same reconstructible cache install's and warm's are, never lock's product. `lockDryRunBaseline` is lock's own preview policy: a lockfile that exists but fails to load is warned about on stderr and then treated the same as no lockfile at all, because a real `lock` run never reads that file - it only overwrites it - so the preview cannot fail on a baseline the command it previews never consults; this policy is specific to a command whose product is to replace the file wholesale, and its named sibling `lockFrozen` draws the opposite conclusion from the identical failure, for the reason stated above.
   A dry run's own collections-tree write is checked, not merely assumed safe. `openCollectionsRoot`'s `create=false` branch runs `probeAnsibleCollectionsUsable` against the `ansible_collections` entry once, at root-open time, before any collection is resolved: `ansible_collections` is usable exactly when `Stat` reports a real directory (a plain one, or an in-root relative symlink to one) or `Lstat` reports it absent entirely; anything else - an escaping or dangling symlink, or a regular file - is classified through `classifyCollectionsRootError`, the identical classifier a real, `create=true` run's own `root.MkdirAll` failure uses, so an escaping or dangling `ansible_collections` symlink fails the preview exit-for-exit identically to a real install (`helpers.ErrCollectionsPathEscape`), and a regular file in its place stays exit-for-exit identical too (both runs leave it unclassified). Below that, once `newInstallTarget` reports a collection's identity safe to use, `installDryRunProbe`'s own `dryRunNamespaceProbe` checks that collection's namespace directory (`ansible_collections/<namespace>`) the same way, but with the opposite rule for a dangling symlink: absent or dangling is fine there (a real install's `RemoveAll`-then-`MkdirAll` of the deeper install path resolves a dangling symlink to nothing and succeeds, then creates the directory fresh), while an escaping symlink or a regular file is a certain per-collection failure, joined behind `helpers.ErrInstallationFailed` exactly as a real run's own extraction failure would be. The asymmetry is structural, not arbitrary: `ansible_collections` itself is created with a bare `MkdirAll` and no preceding removal, so a dangling symlink there defeats it outright, while the namespace directory is always reached through `RemoveAll` first.
   `classifyDryRun`'s per-collection check for install (`installDryRunProbe`) evaluates the same two-step gate `canSkipInstall` itself uses - `installRecordMatches`'s cheap check, then a tally comparison - but calls `checkExtractMarker` directly for that tally step instead of `canSkipInstall`'s own `verifyExtractMarker`: `checkExtractMarker` is the pure half (present/well-formed/tally comparison, no logging, no side effects) that `verifyExtractMarker` wraps with the install path's own logging and a best-effort marker `os.Remove` on a negative outcome. The split exists specifically so a preview can ask whether the marker is still valid without deleting it as a side effect of merely describing it. A collection settled by that gate is pin-consistent by construction - `installRecordMatches` already requires the installed entry's sha to equal a non-empty lockfile pin - so it is reported settled without ever consulting the artifact cache's own recorded digest at all.
   For a collection that is not settled, install's and warm's probes both apply the identical `dryRunPinVerdict` predicate before reporting anything else: a cached artifact whose *recorded* digest (`ArtifactStore.Meta`, never its actual bytes - the cost re-hashing them would add is exactly what this preview exists to avoid) disagrees with a well-formed lockfile pin, under `--offline`, is reported a would-fail: the failure a real run raises at `verifyPinnedSHA`/`warmVerifyAndEnsure` whenever the recorded digest is genuinely the tarball's own digest, the ordinary case the e2e fixtures cover - but a false alarm in the inverse shape, where only the recorded digest was altered and the tarball's bytes on disk were left intact: a real `--frozen --offline` install re-hashes those bytes under a non-empty pin and never reads the recorded digest at all, so the local cache backend still succeeds (measured: exit `0`) where this preview reports a would-fail (exit `7`); the S3 backend does not reach that re-hash at all, because its own `Fetch` re-verifies the freshly downloaded bytes against that same recorded digest first, so there the disagreement fails closed exactly as the preview predicts (`ErrSHA256Mismatch`, `ExitIntegrity`) - the verdict is a refusal, not a prediction, precisely because it is right for one backend and wrong for the other. Online, the identical disagreement produces no verdict at all: a real run's own evict-and-refetch recovery can still repair it there, so reporting a certain failure would be the wrong answer. A malformed or absent recorded digest is likewise never a verdict - the shape gate belongs to `resolveArtifactSHA` on the real path, and this preview leaves it there rather than branching its own verdict on which backend produced the value. What remains genuinely undetectable by either probe, in either direction, is whether the recorded digest still describes the bytes actually on disk: bytes that silently drift while the recorded digest is never updated report a false "fine" that a real run would then fail on either backend, and a recorded digest that is itself altered while the bytes are left intact reports a false would-fail that a real run on the local backend would then succeed against (the S3 backend fails there too, as covered above). Closing either gap would mean re-hashing the artifact's actual bytes, a full object download on the S3 backend. `classifyDryRun`'s own `--frozen --offline` warning discloses that narrower residual rather than hiding it.
   `warmDryRunProbe` is warm's own predicate, and it is deliberately not the same shape as install's: a collection is settled only when the artifact is cached **and** its extracted tree is ready (`extracted.Store.Ready`) under a sha named from the lockfile pin (`col.SHA256`) or, failing that, the snapshot's own warmed record (`warmDryRunSHA`) - cache presence alone is never enough, because the artifact store and the extracted store are independent: `--s3-bucket` makes the first remote while the extracted store is always local to `cfg.CacheDir`, so a fresh runner against a warm bucket can have every artifact cached and not one extracted tree. `dryRunPinVerdict` is checked before `extracted.Store.Ready` here and, when it fires, overrides a settled verdict outright rather than merely preceding it, because a real warm's own pin check (`warmVerifyAndEnsure`) runs before `Ensure` ever populates or reuses the extracted tree - the opposite order from install, where a settled match already implies pin consistency by construction. The named sha itself is still never re-derived from the artifact's actual bytes, so under `--frozen --offline` a settled verdict can still precede a real run that fails closed with `helpers.ErrSHA256Mismatch`, specifically when the tarball's bytes drift while its recorded digest does not; `classifyDryRun`'s own `--frozen --offline` warning discloses this narrower residual rather than hiding it.
   `installDryRun` and `warmDryRun` build their failure error through the identical `failureSummary.installError`/`warmError` headline a real run's own `finalizeInstall`/`warmWithState` use, joining every recorded per-collection cause behind it exactly as a real run does - so a would-fail collection's exit code matches what a real run would exit with for the identical underlying cause: `cmd/go-galaxy/exitcode`'s `ExitIntegrity` behind a `helpers.ErrSHA256Mismatch` cause (`dryRunPinVerdict`'s own verdict), `ExitInstall` otherwise (the offline case, or a collections-tree write a real install would refuse), never a single fixed class for every would-fail collection regardless of cause.
   `--refresh` (`cfg.Refresh`) vetoes exactly the resolve-snapshot reuse `resolveCollectionsInternal` (`resolve.go`) would otherwise take, for every caller of that function - `prepareInstallPlan`'s own `resolveOrLoadLockfile` for `install`/`warm`, and `lockWithState`'s resolve for `lock` alike; see that function's own doc comment for the full version-free/version-scoped predicate `--refresh` implements (which cached answers it bypasses and which it leaves alone), and `refreshBypassesSnapshot`'s own doc comment for why `--offline` outranks it. Under `--frozen`, `install`/`warm` never reach `resolveCollectionsInternal` at all - `resolveOrLoadLockfile` takes the `cfg.Frozen` branch straight to the lockfile instead - so `--refresh` has no resolve snapshot to veto there, a property rather than a special case: under `--frozen` the lockfile IS the resolution. `lockWithState` always calls `resolveCollectionsInternal` regardless of `cfg.Frozen`, which is what makes `lock --frozen --refresh` meaningfully different from `lock --frozen` alone - see `lockFrozen`'s own doc comment below, which states the gate's mirroring of `lock`'s own resolution per flag set, not per command.
3. `installLevels` - for each level, fan out installs to `cfg.Workers` goroutines (semaphore-bounded). On any failure within a level, the loop breaks before the next level. The prefetcher hands off downloaded artifact metadata via `prefetch.Wait(key)`, which also hands the install worker the artifact the prefetcher already downloaded (its temp path and verified sha), so the worker reuses those already-verified bytes through the same pin/hash and ingest verification instead of fetching the artifact a second time - for the S3 backend this eliminates re-downloading the object the prefetcher had just uploaded. A cache-hit artifact that fails its pin/hash check or fails to extract is evicted (tarball plus sidecar) and refetched exactly once, then re-verified and re-extracted; offline runs never evict. The same bounded evict-and-refetch-once also covers a cache-resident object that fails a backend's read-time integrity check (the S3 store verifies a fetched object's sha256 on read against the canonical lowercase form only, matching the local backend's own sidecar rule - a case-only difference is a retryable `ErrSHA256Mismatch`, not a hard failure, and self-heals through this same evict-and-refetch since the refetch re-commits canonical lowercase metadata; surfaced from `prepareInstall` itself), not only a pin/hash or extract failure, and the `warm` command shares this same bounded recovery through the same `prepareWithRecovery` helper, so the recovery is not limited to `installLevels`.
   The extracted store verifies that a tarball hashes to its sha key before ingesting it, so a rotted or tampered cached tarball can never poison the shared content-addressable store with content that does not hash to its key; do not reintroduce a permissive ingest that skips this check.
   `markerRel` (formerly `extractMarkerPath`) is the single validating chokepoint for the extract-marker path: it rejects any sha that is not `helpers.IsSHA256Hex` before computing `path.Join(target.rel, helpers.ExtractMarkerPrefix+sha)` - a slash-separated path relative to the run's rooting boundary (see below), not an OS-native absolute string - since a non-canonical sha - in particular a leading `..` - fuses with the `.extract-done.` prefix into a real "up one directory" element, made unbounded by a leading `./`. `target.root` is a real backstop behind this guard now, not the only defense the way an `installPath`-based join once was: even a traversal sha that somehow survived the `IsSHA256Hex` check would still have to pass through `target.root`, which refuses to resolve a path component escaping `cfg.DownloadPath`. Every caller goes through this one function - `writeExtractMarker`, `checkExtractMarker`, `verifyExtractMarker`, and `installRecordMatches`, which previously inlined its own copy of the join in a different file - and no other construction of that join may exist.
   `verifyPinnedSHA` checks a lockfile pin against `resolveArtifactSHA`'s result, which for a pinned collection always re-hashes the actual downloaded or on-disk bytes rather than trusting a cache-hit's recorded metadata sha, so a `--frozen` install is immune to a poisoned snapshot: a poisoned download URL or sha fails the install closed instead of installing attacker content.
   `helpers.ArtifactDownloadDeadline` (15 minutes) is a hard wall-clock ceiling on one artifact acquisition - not a collection and not a run - spanning the response, the streamed body, extraction running alongside it, the cache commit, and every retry attempt and backoff sleep together as one shared budget, applied via `context.WithTimeout` at exactly two points, both in `internal/galaxy/collections`: `downloadCollectionToCache` (the single funnel for a fresh origin download, shared by install, warm, and the prefetcher) and `fetchArtifact`'s cache-hit arm, which on the S3 backend is a full artifact body transfer over HTTP too. It is applied only here, never inside `internal/cache/*`, so nothing crosses the `Backend` seam - a backend merely honors the context it is handed, exactly as it already honors caller cancellation. `artifactDeadlineError` deliberately renders its cause with `%v`, never `%w`: the cause is `context.DeadlineExceeded`, or `context.Canceled` in a watchdog race, and `exitcode.FromError` checks `context.Canceled` first, so wrapping it would report a hostile server's slow drip as an operator's own Ctrl-C. The sentinel sits outside `prepareWithRecovery`'s evict-and-refetch class for the same reason `helpers.ErrMalformedArtifactSHA256` does - eviction cannot repair a budget, only a bad value - and `artifactDeadlineError` explicitly excludes `helpers.ErrSHA256Mismatch` for the identical reason `prepareWithRecovery` treats it separately: an integrity failure keeps its own identity even when the budget expires in the same instant.
   Out of scope for this deadline: Galaxy metadata JSON fetches and the S3 snapshot/project-registry state objects are bounded by their own, separate deadlines instead (`helpers.MetadataFetchDeadline`, `helpers.StateObjectDeadline` - see "Galaxy server resolution and authentication" and "Cache backend abstraction" respectively); a backend's `Has`/HEAD probes and the S3 lock heartbeat remain unbounded by any of the three, since none of them streams a response body a drip could stall.
   Exit-code note: a deadline failure or a stalled read joined behind `helpers.ErrInstallationFailed`'s per-collection aggregation classifies by that aggregation's own headline - the install-failure class - the same as every other per-collection cause. Unaggregated, a stall or a deadline classifies as the network class instead. None of the four sentinels this rule covers - `helpers.ErrArtifactDownloadDeadline`, `helpers.ErrReadStalled`, `helpers.ErrMetadataFetchDeadline`, `helpers.ErrStateObjectDeadline` - ever classifies as the interrupt class, because each renders its context cause (`context.DeadlineExceeded` or `context.Canceled`) with `%v` rather than wrapping it with `%w`. The general rule the next sentinel author must inherit: a sentinel describing why work ended must never leave a context sentinel reachable through `errors.Is`, because `exitcode.FromError` checks `context.Canceled` ahead of every other class and would otherwise report a hostile or degraded server as a caught Ctrl-C. That rule has two enforcement points, not one. The first covers `helpers.ErrReadStalled` and `helpers.ErrArtifactDownloadDeadline`: `internal/galaxy/fetch`'s `watchdogBody.Read` is the sole producer of `helpers.ErrReadStalled`, and `internal/galaxy/collections/deadline.go`'s `artifactDeadlineError` is the sole renderer of `helpers.ErrArtifactDownloadDeadline`. The second enforcement point, covering the metadata and state-object deadlines, is `internal/galaxy/cache`'s `deadlineError`: it renders both `helpers.ErrMetadataFetchDeadline` and `helpers.ErrStateObjectDeadline`, and its own `%v`-not-`%w` rendering is pinned by `TestDeadlineErrorClassification`'s "cause wraps context.DeadlineExceeded" and "cause wraps context.Canceled" rows in `internal/galaxy/cache/deadline_test.go`, run against both sentinels. `deadlineError` is deliberately not unified with `artifactDeadlineError` despite the shared shape: it additionally requires a causal precondition - the error being normalized must itself carry a context signal - because its two surfaces (a metadata fetch and a persisted cache-state operation) have wide error vocabularies and one of them, the metadata surface, is load-bearing for routing a 404/401/403/5xx through the server-list walk by HTTP status rather than by a deadline race; retrofitting that same precondition into `artifactDeadlineError` would instead de-fang the killing mutation pinned for its own `helpers.ErrSHA256Mismatch` exclusion, since a sha mismatch carries no context signal and would pass the precondition either way. `internal/galaxy/fetch`'s `watchdogBody.Read` remains the only producer of `helpers.ErrReadStalled`; every site that later carries the error - `annotateSaveFailure`'s `"%w; snapshot save failed: %w"`, `metadata.go`'s `"failed to load root metadata: %w"`, and every other `%w` on the path - is a faithful propagator and must keep wrapping with `%w`, because a save or fetch that genuinely failed due to caller cancellation has to keep `context.Canceled` reachable. So `helpers.ErrReadStalled`'s own invariant has one enforcement point and one pin, in `internal/galaxy/fetch/watchdog_test.go`: `TestWatchdogBody_StallErrorDoesNotMatchContextCanceled` (the rendering) and `TestWatchdogBody_FiredWatchdogYieldsToParentCancel` (the `parentCtx.Err() == nil` guard, whose removal no test outside that package catches). A producer regression re-opens every propagation path at once, which is why that pin lives at the producer rather than being duplicated per carrier.
4. `finalizeInstall` - save the snapshot back to the backend; if any failures, return a wrapped `ErrInstallationFailed`. The save no longer short-circuits the failure classification: whether it succeeds or fails, the returned error still classifies by the collection-failure count (a save failure is folded in via `annotateSaveFailure`, so `errors.Is` still matches both), so `installWithState` reaches `writeRunMetrics` and the run metrics report is written even when the save itself failed.
   `installLevels` (and, for `warm`, `warmCollections`) no longer hands `finalizeInstall` a bare failure count: both return a `failureSummary` (`internal/galaxy/collections/failures.go`), built by a `failureRecorder` that appends each per-collection cause under one lock alongside its `atomic.Int32` count, so the two can never drift apart. `finalizeInstall`/`warmWithState` render the summary's headline as a single line (`"%w for %d collections"` / `"%w: warm failed for %d collections"`) while still joining every recorded cause behind it via `errors.Join`, so `errors.Is` matches both `helpers.ErrInstallationFailed` and any per-collection sentinel it carries - including `helpers.ErrSHA256Mismatch`/`helpers.ErrMalformedArtifactSHA256`, which is what lets `cmd/go-galaxy/exitcode`'s integrity check see through the headline to an integrity cause underneath. The rendered message deliberately stays one line rather than listing every cause: each cause was already printed to stderr in real time by the worker that hit it (`"Failed: %s.%s error: %s"`), so repeating them in the tail error would duplicate the log, not add information.

Every install-side write - from the collection's install directory down through its `.info` sidecar - is rooted. `installWithState` opens a single `os.Root` via `openCollectionsRoot` at `cfg.DownloadPath`, once per run and before requirements are even loaded, then threads it through `installDeps.root`/`prefetchDeps.root` to every downstream consumer: the prefetcher and every install worker across every level. This lives in `installWithState`, deliberately not in `initInstall`: `initInstall` is shared with `warm` and `lock`, and a warm-only machine never touches the collections tree at all - it has no `cfg.DownloadPath` to root in the first place, so `warmWithState` hands `newInstallDeps` a nil root, which `newInstallTarget`'s own nil-root guard turns into a fail-closed `ok=false` on any accidental use rather than a nil-pointer panic. `ansible_collections` itself is created once, through that root, at the same time the root is opened - not once per collection - because it is a prefix every collection in a level shares: without that, a symlinked `ansible_collections` would surface as one identical escape failure per collection in a 200-collection level instead of a single one for the whole run. `installTarget`, built once per collection by `newInstallTarget` (`internal/galaxy/collections/installroot.go`), is the single chokepoint for both of a collection's on-disk locations - its install directory and its `.info` sidecar - replacing the former, separately-guarded `collectionInstallPath` and `collectionInfoDir`: one guard covers both locations now, using the same `helpers.IsPathElement` validation of namespace, name, and version that only the sidecar path had before, and the same predicate `cleanup.removeInstalled` applies on the delete side, so the deleter never refuses an install or sidecar directory this pipeline created as an unsafe identifier.

`os.Root` contains path resolution, not identity, and two of its properties are easy to get wrong when extending this. First, `os.OpenRoot` itself follows a symlink when *establishing* the root - the same as a plain `os.Open` would - which is exactly what keeps a symlinked `cfg.DownloadPath` working (see the drop-in-compatibility note in the "Project" section above), and exactly what would make rooting one level lower, at `ansible_collections` instead of `cfg.DownloadPath`, catastrophic: a symlinked `ansible_collections` would then be established as the root itself, with no `os.Root` protection left over that first hop. Second, below the established root, a component symlink is allowed with a relative in-root target and refused with an absolute one, even when that absolute target geometrically resolves back inside the root, because `os.Root` never consults the absolute filesystem namespace at all.

`os.Root` also cannot see hardlinks: a hardlink is not a path, it is a second name for an inode the kernel already resolved before `os.Root` was ever involved, so containment alone says nothing about a pre-planted hardlink sitting at a leaf name inside an already-rooted directory. What closes that variant is not the root but an unconditional remove-before-write at every leaf this pipeline writes: `extractCollection` resets the install directory (`RemoveAll` then `MkdirAll`, both rooted) before unpacking, `writeGalaxyInfo` resets its `.info` directory the same way before writing `GALAXY.yml`, and `writeExtractMarker` removes any existing marker before writing a new one - each guarantees its write lands on a name this run just created, never on a name that might already resolve to attacker-controlled content.

This makes the collections tree a write-side containment boundary, not a trust boundary: the same repository that could plant a symlink under `cfg.DownloadPath` can also redirect `collections_path` itself through `ansible.cfg` discovery, so the guarantee is containment relative to the configured path, never that the configured path is trustworthy - redirecting `collections_path` is an operator-visible configuration act, and writing collections where the tool was told to write them is not a vulnerability. The residual is disclosed, not hidden: a live local writer racing inside a collection's own install directory during extraction is not defended against - `cleanup`'s own `removeInstalled` already declines the identical case in the same terms (see "Cleanup pipeline" below).

The cache tree carries the same containment boundary, established the same way and for the same reason. `internal/galaxy/extracted`'s `Store` resolves every path it creates, renames, lists, or removes through an `os.Root` opened at `cfg.CacheDir` - never one level lower at `<cacheDir>/extracted`, since `os.OpenRoot` would follow a symlink at that name and adopt whatever it points at. Without that root, a symlink planted at `<cacheDir>/extracted` redirects `Sweep`'s per-entry `RemoveAll`, `extractInto`/`Promote`'s `RemoveAll`+`Rename` pair, and `IngestReader`'s temp creation, all of which reach a path the operator never configured; `cfg.CacheDir` itself is settable from the repository's own `ansible.cfg` (`[galaxy] cache_dir`), so this is the same shape as the collections tree, one severity step down. The store directory being present but unusable - an escaping symlink, or a regular file in its place - is reported as `extracted.ErrStoreDirUnusable` rather than as the kernel's own `EEXIST` from `mkdirat`, which names neither the path nor the problem. Two path forms cross this seam and are re-derived rather than trusted: `Promote` and `Discard` take a temp path a caller received from `IngestReader` and refuse (`ErrTempOutsideStore`) any that does not sit under the cache directory, so the `RemoveAll` behind them can never be aimed at an arbitrary path - which is why `downloadCollectionToCache` calls `Discard` instead of `os.RemoveAll` on its own failure arms. What stays deliberately unrooted is the unpack itself: `archive.ExtractTarGz` is handed an ordinary path to a temp directory the root created moments earlier, exactly as `extractCollection` hands it `target.path`, and for the identical reason recorded there.

The local cache backend needs no root of its own, and that is a property of its layout rather than an omission. `helpers.ArtifactKey` percent-escapes the filename, so every path that backend builds is the cache directory plus exactly one element, leaving the entry itself as the only thing a local writer could turn into a symlink - and both mutating operations refuse to act through one structurally: `Commit`'s `os.Rename` replaces the link and `Delete`'s (and `ClearCacheFiles`'s) `os.Remove` unlinks it, neither following it to a target. The residual is the Bolt snapshot file and the instance lock file: bbolt and the flock both take a path and neither accepts an already-open descriptor, so a symlink planted at one of those two leaf names is followed. That is disclosed rather than closed, and it is a single-file redirect inside a directory whose write access this project's trust model already treats as equivalent to writing the snapshot itself.

`writeGalaxyInfo`'s `<ns>.<name>-<version>.info/GALAXY.yml` sidecar path is built through `newInstallTarget` (see above), using the resolved `col` identity. `meta`, when present, contributes only `download_url`, `version_url`, and `signatures` to the sidecar's body - never a path component - so a server's version metadata disagreeing with `col`'s resolved identity can never affect where the sidecar lands. A refusal (an unsafe `col` component) warns and continues rather than failing the collection, since the collection's tree is already extracted by the time `writeGalaxyInfo` runs.

### Cleanup pipeline (`internal/galaxy/cleanup`)
Walks every project recorded in the registry, scanning only the fixed `<collections_path>/ansible_collections/<namespace>/<name>/MANIFEST.json` layout (not a full `**` tree walk), through a single `os.Root` opened per project at its collections path - never one level lower, at `ansible_collections` itself, for the identical reason the install side roots at `cfg.DownloadPath` rather than lower (see "Install pipeline" above): `os.OpenRoot` follows a symlink when establishing the root, so rooting at `ansible_collections` would just adopt whatever it points at, leaving nothing left to refuse. A project whose `ansible_collections` entry is absent is skipped, the ordinary case; one whose entry resolves outside its collections path - an escaping symlink, most commonly - is skipped too, but with a single per-project warning naming it, since this is a misconfiguration local to that project, and every other project's cleanup still proceeds unless some recorded project's `requirements.yml` fails to load for any reason other than a plain `fs.ErrNotExist`, which aborts the whole run for every project at once. A resolved workspace that still fails a subsequent read (a genuine IO error, not an escape) aborts the whole run without deleting anything; an unreadable or unparseable `requirements.yml` aborts the run the same way, for any recorded project regardless of whether its own workspace was scanned this run - see the reachability paragraph below for why. Within a project that does scan, an individual `MANIFEST.json` that is not a regular file - a symlink of any shape, a directory, or anything else in its place - is skipped with its own warning naming the path, while the rest of that project's collections are still scanned and cleaned up normally: the leaf is `Lstat`-ed and accepted only when that reports a regular file (`manifestIsRegularFile`), a predicate on the entry's mode rather than a symlink-specific blocklist, so a future implementer narrowing the check to symlinks alone would still let a directory or any other non-regular shape through unguarded. A scanned collection's namespace and name are always the two `ansible_collections/<namespace>/<name>` path components the scan walked through to find its manifest, never a value the manifest itself declares - the manifest contributes only the version and its dependency edges - so no MANIFEST.json content can redirect a deletion at a different collection's directory. The version is the one identity component still read from the manifest, since nothing else on disk records it; a lying version's blast radius is bounded to a fixed prefix, not to a unique target - because `-` and `.` are both legal inside a walked path element, `<ns>.<name>-<version>.info` and `<ns>-<name>-<version>.tar.gz` are ambiguous concatenations, so walking namespace `a`, name `b`, with a manifest lying that its version is `c-1.0.0` produces a sidecar name and an artifact filename byte-identical to what a genuinely, legitimately installed `a.b-c@1.0.0` would itself produce. The impact stays narrow regardless: the sidecar `RemoveAll` failure this could cause is already ignored (`removeInfoDir` is best-effort), and an artifact cache-slot eviction self-heals on the next refetch. Containment is unaffected either way - `removeInstallPath` joins only Namespace and Name, so the version never participates in a directory path at all. Reachability is computed in two passes over the registry, in sorted project order: every project's workspace is scanned into one shared index first, and only then is every recorded project's requirements file resolved against that complete index - so whether one project's requirement, or one MANIFEST's dependency edge, keeps another project's copy alive never depends on which project the map happened to yield first. A recorded project contributes its roots regardless of whether its own workspace was scanned this run; a project whose requirements file no longer exists contributes no roots and is named in a single warning, while one whose file fails to load for any reason other than a plain `fs.ErrNotExist` aborts the whole run without deleting anything, since roots that cannot be determined could have been protecting any project's copies. Every on-disk copy of an unreachable `ns.name@version` key is removed together with its cached artifact - keyed by that entry's persisted `InstalledEntry.Source` via `helpers.ArtifactKey`, so the removal targets the same server-scoped cache slot the install actually used - skipping (with a warning) any unsafe identifier and refusing, through its own separate `os.Root` opened at deletion time, any path resolving outside a project's `ansible_collections` directory. Whenever this package prints an identifier assembled solely from components `helpers.IsPathElement` has validated - a removal or would-remove report line's `ns.name@version` key, chief among them - that identifier can never carry a character able to forge an extra printed line or drive a terminal, since `IsPathElement` itself now rejects every such character (see its own doc comment); those report lines print such an identifier with a bare `%s` rather than needing a `%q` at each call site for exactly that reason. A value this package cannot make that guarantee about prints `%q` instead: a `MANIFEST.json` path built from a raw directory-listing name before validation ever runs, or an extracted-store entry name read back from a local directory listing a local writer controls. The extracted-store sweep keeps entries referenced by the persisted snapshot's installed set, union its still-fresh warmed set, rather than an on-disk scan, so an absent workspace does not wipe the extracted cache; `--dry-run` reports both the collection-removal and extracted-store sweep candidates without deleting, for exactly the projects a real run would scan - a project skipped for an absent or escaping workspace contributes no candidates in either mode, so a dry run never previews a removal a real run could not perform. A warmed entry is the only signal that a warm-only machine (whose `ansible_collections` workspace does not exist at all, so its project is skipped entirely and never contributes an installed entry) still wants its extracted tree kept; it carries no project and no install path, so it expires purely by age (`helpers.WarmedEntryMaxAge`), and it is deliberately not subject to the installed half's `wouldRemove` exclusion - a key that is both installed-unreachable and warmed still keeps its tree, since warm's intent is independent of install reachability. `warm` is the only writer of the warmed set (`recordWarmed`, called from `warmOne` on every successful collection, cache hits included); `install` and `lock` deliberately never write it. `sweepLegacyArtifacts` additionally purges, unconditionally and independent of reachability, any tarball still cached under the pre-multi-server flat key shape (no server scope at all): the one-time migration cleanup for the schema-4-to-5 artifact-key change, since nothing can ever look up that shape again. The snapshot-driven extracted-store sweep requires a snapshot that has ever recorded on-disk content (`Store.HasRecordedContent`), not merely one that was written (`Store.WasPersisted`), while the snapshot save requires the latter; each is skipped otherwise with a single operator warning naming which of the two conditions failed, while `removeUnused` (workspace-scan-driven) and `sweepLegacyArtifacts` are driven by on-disk evidence and stay unconditional regardless of whether a snapshot was loaded. A sidecar directory written by a pre-fix binary under a server-supplied version is orphaned and deliberately not swept: the `ansible_collections` tree is shared with real `ansible-galaxy`, which writes the identical `*.info` layout, so deleting unrecognized `.info` directories would destroy another tool's data - and no run has the information to locate such an orphan anyway, since the escaping name was a function of the server's version metadata, which was never persisted.

### Output / progress
`progress.New` returns a `Printer` (also satisfies `io.Writer` so `log.SetOutput(p)` redirects all stdlib logging through it). In verbose mode, `Debugf` and `DebugSincef` are active; in quiet mode the transient tier (`Printf`, `Write`) and the debug tier are suppressed, while the result tier (`PersistentPrintf`, `Okf`, `Errorf`) always emits. In non-TTY normal mode (typical CI), all non-debug output is printed as plain lines with no spinner, instead of being silently dropped. Regular output goes to stdout; `Errorf` (both the method and the package-level helper) goes to stderr, so diagnostics do not contaminate stdout consumers. Color on the status markers is decided per destination rather than once per process (`internal/progress`'s `stream` binds a writer to whether it accepts color), because `go-galaxy install > install.log` leaves stderr a terminal while stdout is a file and one decision would get one of the two wrong; `colorEnabled` is the rule - `NO_COLOR` (non-empty) disables, `CLICOLOR_FORCE`/`FORCE_COLOR` (non-empty and not `0`) force, otherwise the destination must be a character device - and `NO_COLOR` deliberately outranks the force variables, since an opt-out another variable can override is not one. The package-level `Okf`/`Errorf` resolve their destination on every call rather than once at construction, because they own no `Progress` and are the path `cmd/go-galaxy/main.go` prints a run's final line through. The spinner keys on stdout being a terminal and is deliberately NOT gated on color, so `NO_COLOR` does not silently take it away. None of this touches the sanitization boundary: the escape sequences involved come from this package's own constants, never from input, which is why the rule below is about the payload rather than the decoration. Use `Output.Errorf`/`Okf` from inside workers - the printer is goroutine-safe.

An operator-facing line may carry text this program does not control - a Galaxy server's error text, a requirements file, a manifest, a filesystem path - so `internal/safeout` is the sanitization boundary for all of them: `safeout.Clean` replaces a character with U+FFFD exactly when it is in C0 (U+0000-U+001F), is DEL (U+007F), or is in C1 (U+0080-U+009F), and is not `\n` or `\t`, plus every byte that is not part of a valid UTF-8 encoding, so the result is always valid UTF-8; and `safeout.NewWriter` applies it per `io.Writer.Write` call for a caller that composes output outside `progress.Progress` (`cmd/go-galaxy/commands/tree.go` and `explain.go` wrap their output writer this way, since a lockfile's Name/Version/Source/SHA256/Deps are printed verbatim). Inside `internal/progress`, every line the package writes funnels through `writeLine`, whose governing rule is structural, not conventional: sanitize the payload, decorate afterwards, never sanitize a line that has already been decorated. `writeLine` takes the message as `safeout.Text` - a string that has already passed through `Clean` - so a plain string cannot be passed where `Text` is required, and a prefix this package declares (a colored marker, a debug tag, a timing string) is never itself subject to `Clean`.

## Conventions

- **Dependencies are gated** by `depguard` in [.golangci.yml](.golangci.yml). Adding a new external dependency requires editing the allow-list. Standard library + the listed third-party modules are the entire palette.
- **Linter is strict**: `default: all` minus a small disable list. Common offenders to watch for: `lll` (140 cols), `fieldalignment` (struct field ordering), `revive`/`staticcheck` package comments. Run `just check` and `just lint` before committing.
- **Errors**: package-level sentinel errors live in `internal/galaxy/helpers` (e.g. `ErrInstallationFailed`, `ErrDuplicateCollectionKey`). Wrap with `%w` when crossing layers.
- **Concurrency**: per-level worker pools use a buffered-channel semaphore (`sem := make(chan struct{}, cfg.Workers)`) plus `sync.WaitGroup` (`wg.Go` from Go 1.26). Failures are tracked with `atomic.Int32`.
- **Bolt buckets and snapshot file names** are constants in `internal/galaxy/helpers`. Reuse them rather than string-literaling.
- **Defensive-only guards need no per-bucket coverage.** Nil-receiver guards on `*Store` methods and the per-bucket `json.Unmarshal` error path inside `loadBucket` callbacks are defensive-only; one representative case (`TestLoadRejectsCorruptResolvedEntry`) stands in for the shared `loadBucket` error-wrapping behavior instead of a test per bucket. The list is closed: anything outside it is covered by "Documented-uncovered is a legitimate outcome, within a boundary" below, stated in place at the site.
- **A comment may claim only what the code proves.** Prose that generalizes past what was built, or past what was actually run, fails silently: an absolute quantifier ("at most two", "when and only when", "never per attempt") that was true when written is false one exception later and nothing announces it. The rules below bind prose that makes a claim, not every comment:
  - **A killing mutation may be described only after it has been run**, with its real failure output quoted. The ban is on the claim, not on any particular wording: an unrun mutation stated in the conditional - "would fail with", "would panic", "this assertion catches it" - is regularly wrong about the message, about which assertion fires, or about whether the test fails at all. This binds only a comment asserting that a mutation kills; it is not a requirement to add a mutation paragraph to every test. Outside such a claim the same words are fine - `dryrun.go`'s `"%d would fail"` report line, or a positive control's "not itself what would fail this scenario" - so this is a reading, not a grep. The quoted failure output is also line-count-neutral: a mutation paragraph sits immediately above the assertion it quotes, so inserting the paragraph after running the mutation shifts that assertion's own line number and silently invalidates the quote - write every mutation paragraph in full first, with placeholder line numbers of the same shape, run every mutation against that now-stable file, then substitute only digits and message text in place, changing no line counts; the file the mutations ran against must be line-for-line identical to the file that ships, paragraphs included.
  - **An assertion inside a chain of `t.Fatalf` checks is pinnable only if some reachable state satisfies every assertion above it while failing that one.** Two assertions on mutually exclusive error signatures cannot both be pinned by a fixture that produces a single failure: whichever comes second can never be the first failing line. An assertion that fails this test is documentary, not pinned - say so where it sits, or drop it.
  - **A refusal test proves nothing without a positive control on the same fixture.** The fixture must be shown capable of acceptance; otherwise "it refused" is indistinguishable from "it never reached the check".
- **A doc claim about when a rule applies must be a predicate, not a list of call sites.** An enumeration of the places that reach a classification goes stale the moment a place is added, and nothing fails when it does - the reader is simply misinformed. Phrase it as a property of the value or of the error tree ("whenever X is joined behind Y"), which survives call sites coming and going.
- **A comment describes the code, not the change that introduced it.** "this change", "this commit", "before this change", "now that we" narrate a diff nobody reading the file later can see. Describing a historical artifact the code still handles is not narration and stays: `legacyArtifactKey`'s "the shape every artifactKey used to build before it gained a server-fingerprint prefix" is the specification of what that function purges, and `s3/retry.go`'s "the production stall error no longer carries context.Canceled" states a current cross-package invariant. The test is whether deleting the past tense would delete information about today's code.
- **Verify prose against the working tree, not the diff.** `git diff` does not see untracked files, so a sweep for stale or leaked wording over a change that adds files skips exactly the files nobody has reviewed yet. Scan the diff and the untracked paths from `git status --porcelain` together.
- **Documented-uncovered is a legitimate outcome, within a boundary.** A behavior that is genuinely impractical to test - a real byte-drip stall against a real clock, an OS-level failure with no injection seam - may be left uncovered, but only where that is stated in place, on the code or test it concerns, naming what is uncovered, why it is impractical, and what is lost if the code it guards is removed (`downloadCollectionToCache`'s note on its outer `artifactDeadlineError` call is the shape). It is not a license to skip a test that is merely inconvenient. And it exempts the behavior, never the register: an untested property is written as untested, not asserted as an invariant a reader will take as verified.
- The `Justfile`'s `LDFLAGS` injects `Version`, `Commit`, `Date`, `BuiltBy` into `cmd/go-galaxy/main.go`. Don't add module-time fallbacks elsewhere.

## Multi-agent workflow & rules

- **Subagents cannot call each other.** Claude Code subagents are terminal: each returns a report and cannot invoke another agent. All routing goes through the main thread, or through the deterministic orchestrator in [.claude/workflows/architect-pipeline.js](.claude/workflows/architect-pipeline.js) (run via the `Workflow` tool or `/gg-pipeline`).
- **The architect gates everything.** For a non-trivial change the order is: architect (design, approve/reject) -> developer (implement) -> architect (review) -> tester (tests + coverage) -> architect -> security (audit) -> architect -> tech-writer (docs) -> architect (sign-off back to the main thread). The architect loops work back to the developer on any `rework`, and only signs off when it is "written ideally, it will not get better than this".
- **The architect defaults to NO.** Under-specified, architecturally wrong, unjustified-dependency, or low-value requests get rejected, not coded around.
- **English only.** All code, comments, tests, docs, and other prose are in English; the tech-writer enforces it.
- **Prose written in passing is still prose the tech-writer reviews.** A developer that writes any prose while implementing - doc comments, test commentary, documentation - must list every file it touched for prose in its report. The tech-writer's pass is otherwise scoped to what it was told about, and the files nobody flagged are exactly the ones carrying unreviewed claims.
- **Hyphen-minus only.** Never an em (U+2014) or en (U+2013) dash anywhere - prose, code, comments, or commit text.
- **Efficiency is a first-class requirement,** not a nice-to-have: minimal allocations per tick, pre-sized buffers, no needless copies on hot paths.
